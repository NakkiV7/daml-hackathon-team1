Problem0:00 – 0:15

The usual answer is to hand the agent a wallet key.

If the key is in the agent's hands, the only thing between a manipulated model and the money is the model's own judgement. In May 2026 a Morse-code-encoded instruction persuaded an AI trading bot to drain about $150k: the safety layer decoded the message, then obeyed it.

So the limit cannot live in the model. Nor in our backend, because anyone reaching the ledger directly would walk around it. It lives in the contract.

Why the backend exists at all

Two reasons only: the client-credentials secret cannot ship to a browser, and every ledger call needs a fresh bearer token. It adds no rules of its own. Remove it and the caps still hold.

The same path for a language model

An MCP server exposes pay, revoke and state to an LLM. Those tools call the same dispatch as the buttons, so an LLM talked into overspending is refused by Canton, not by a check in our code.

The contractproj/daml/Mandate.daml

Seven rules, each one line, all inside the Charge choice.

-- both parties must consent for the mandate to exist
signatory owner, spender

choice Charge : ContractId Mandate
  with amount : Decimal
       payee  : Party
  controller spender        -- the agent acts alone
  do
    now <- getTime
    assertMsg "mandate expired"            (now < expiresAt)
    assertMsg "amount must be positive"    (amount > 0.0)
    assertMsg "mandate revoked"            (not revoked)
    assertMsg "charge would exceed the period cap"
              (curPeriodSpent + amount <= periodCap)
    assertMsg "charge would exceed the cap"
              (spent + amount <= cap)
    assertMsg "payee not in allow-list"
              (payee `elem` counterparties)
Why this placement matters

controller spender means the agent's authority alone drives a charge, which is the point: no human signature per purchase. The assertions sit in the choice body, so they bind anyone exercising it. The quoted strings are exactly what the browser displays, because Canton returns them as AssertionFailed.

Revocation, separately

choice Revoke : ContractId Mandate
  controller owner   -- owner alone; agent cannot block

Also enforced

ensure holds spent <= cap and periodSpent <= periodCap as invariants on every state transition, so a mandate breaching them cannot exist at all.

Why two steps and not one

The Mandate has two signatories, so it cannot be created by the owner alone, because Daml will not let one party impose an obligation on another. The proposal carries only the owner's signature; accepting adds the agent's. This is the standard shape for any agreement on Canton.

if it stalls

Writes are never retried automatically. DevNet returns 503 while still forwarding the command, so a retry races the original, and Canton then answers SUBMISSION_ALREADY_IN_FLIGHT, after which every contract id we hold is stale. Instead the error surfaces and you press the button again, which is safe because each submission carries a fresh command id.

Test 4 · exceed the period cap0:55 – 1:10

The first thing a judge will try.

fields
Amount 999 · Payee Cloud vendor
press
Charge
expected · refused by Canton
charge would exceed the period cap

Same outcome for 100 000, and for any amount above the remaining daily budget. The mandate is untouched: spent stays at 25 and no audit record of a successful charge is created. The refusal itself is recorded. 

assertMsg "charge would exceed the period cap"
          (curPeriodSpent + amount <= periodCap)

Read the daily cap as a rate limit

A lifetime cap alone lets a hijacked agent drain everything in one minute. The period cap bounds the loss per day, which is what buys a human time to notice and revoke.

the window does not reset on a timer

Nothing in Daml runs on a schedule. Charge rolls the window forward when it next runs, advancing by whole periods from periodStart and never to now. Anchoring to now would let the agent slide the window by timing its charges.

Test 5 · exceed the lifetime capfollow-up question

If asked for the lifetime cap specifically, the daily cap has to be raised out of the way.

A detail worth pre-empting

Unapproved vendor resolves to a real party the node hosts, not a malformed name. So the refusal is genuinely the allow-list rejecting an existing party, rather than Canton rejecting an invalid party id. If a judge types a random string it is refused too, but for the less interesting reason.

also refused

Amount -50 to the approved vendor returns amount must be positive. A negative charge would otherwise run the balance backwards and manufacture headroom.

choice Revoke : ContractId Mandate
  controller owner
  do
    now <- getTime
    newCid <- create this with revoked = True
    create MandateRevokeAudit with
      owner; spender; at = now
      reason = "owner revocation"
    pure newCid

Why a flag rather than simply archiving

Archiving would also stop the agent, since the contract id would no longer exist. Keeping a revoked mandate on the ledger means the owner can still read its final state and tie the revocation event to the record it applies to. Both routes stop the spending; this one leaves better evidence.

Adjust cannot undo it either: it carries the existing fields forward, so revoked stays true, and it needs both signatures regardless.

These records are contracts

MandateChargeAudit is signed by the spender and observed by the owner; MandateRevokeAudit the other way around. Because they are on the ledger they cannot be edited after the fact, which is the property an auditor actually cares about.

why the list is short

Audit contracts accumulate across every mandate this owner has ever held, and testing left 113 of them. The view is scoped to records created since the mandate on screen was granted, so a demo opens clean. The older ones are still on the ledger.

Return the coin sweeps it back so the demo repeats
expected · settlement detail
transferKind: offer · accepted: true

A transfer arrives as direct when the receiver holds a live pre-approval and as an offer otherwise. An offer does not move the receiver's balance until accepted, so we accept on the payee's behalf and the money genuinely lands.

Why Charge does not move the money itself

A token-standard transfer needs disclosed contracts fetched from the issuer's registry for that single transaction. A Daml choice body cannot make an HTTP call to go and get them. So the agent authorises on the ledger first, and only an authorised charge reaches the settlement code at all.

scale, stated plainly

The agent holds about 5 Amulet while its authorisation cap is 500. The cap is therefore demonstrated by refusal, not by exhausting the balance. Each demo costs roughly 0.1 in network fees. Both parties are ours, so nothing leaves the team.

The same mandate, with the same spent, and charging continues from there.
measured
before kill  spent 90.00 of 500.00

The backend keeps only a contract id in memory. On startup it queries the active contract set and adopts the live mandate again. Nothing about the budget was ever stored in the application.

A related refusal, worth expecting on camera

Contract could not be found with id 00…

Every accepted charge archives the mandate and creates a successor, so a second browser tab, or a script run in a terminal, leaves the first view holding a superseded id. The backend detects this, re-reads the current mandate and retries once, so pressing the button again works. It is Canton being strict about contract identity, not a failure.

which failures are retried

Reads are retried, five attempts at a 3 second timeout each. Writes are never retried, because a stalled submission may still be in flight. The heavy /v2/parties read gets the full 30 seconds, since it returns ten thousand records a page.

When it goes wrong on cameraevery message you might see

Each failure has a known cause and a known response.

MessageCauseWhat to do
HTTP 503 … /v2/commands/ DevNet refused a write under load Press the button again. Fresh command id, safe.
SUBMISSION_ALREADY_IN_FLIGHT The same command was submitted twice Wait a moment, then read state. One of them committed.
Contract could not be found Contract id superseded by a charge elsewhere Press again; the backend re-reads and retries.
read operation timed out A black-holed load-balancer address Resolves itself. Retries are automatic on reads.
balance unknown Balance query failed Not a zero balance. Press Re-check.

sender has no spendable Amulet Authorised, but nothing to settle with Return the coin, or ask Cantor8 to fund the party.

None of these are the wallet failing. The wallet failing would look like a charge going through when it should not, and that is the one case none of our twelve tests produces.

Test 12 · the same rules through an LLMMCP

The tools a language model drives reach the ledger by the same path.

An MCP server exposes the wallet as tools over stdio JSON-RPC. Early on those tools called the backend's simulation helpers rather than the live ledger, which would have meant an LLM was policed by Python while the demo claimed Canton was doing it. They now go through one shared dispatch, so the HTTP buttons, the autonomous agent and the LLM all take the same route.

Simulating a manipulated model
Tool callVerdict
pay(25, Cloud vendor)allowed
pay(9999, Cloud vendor)period cap
pay(10, Unapproved vendor)not in allow-list
pay(-5, Cloud vendor)must be positive

The claim this supports

A prompt can talk a model into attempting any of the above. None of it succeeds. The boundary is not in the model's reasoning, nor in the tool layer, nor in our HTTP handler. It is a rule in a contract the model cannot reach.

borrowed vocabulary, deliberately

Google's Agent Payments Protocol calls its primitive a mandate: a signed grant carrying constraints for when the human is not present. Ours is the same idea with the constraints executed by the ledger rather than checked by a verifier, so authorisation and settlement land in one signed transaction.

What is real, and what is notstated before being asked

Overclaiming costs more than an unfinished build.

Live on Canton DevNet
  • The mandate is a contract with a real contract id
  • Lifetime cap, period cap, allow-list, expiry and revocation are enforced in Mandate.daml
  • Every refusal quoted in this deck is an AssertionFailed returned by Canton
  • Charge and revoke audit records are contracts on the ledger
  • Canton Coin moves and the payee's balance changes
  • Killing the backend loses no state
  • The MCP tools take the same path as the UI
Not done
  • Settlement moves 0.1 at a time against a balance of about 5, so the cap is proven by refusal rather than exhaustion
  • The allow-list is fixed when the mandate is granted; changing it needs Adjust and both signatures
  • Period windows roll forward on the next charge, not on a timer
  • Charge does not itself transfer funds, for the registry reason given earlier
  • Tests share a package with the templates, which would bloat a production participant

The honest gap is settlement scale, not enforcement. Every limit is real; the pot of money behind it is small.
